Lesson 0001

The 4-Phase Senior AI System Design Blueprint

How to transition from ML modeling intuition to structured, distributed production systems leadership in 45-minute technical interviews.

⏱ 12 min read & practice 🎯 Target: Senior & Staff AI Interview Loops 📄 Open Cheat Sheet Reference

The "Data Scientist Trap" in System Design

When an interviewer asks: "Design a real-time AI code completion assistant like GitHub Copilot," candidates with strong ML backgrounds often commit a fatal error: they immediately dive into model choices, tokenizer types, or fine-tuning loss functions.

To an interviewer assessing a Senior or Staff AI Engineer, this is an immediate red flag. A production AI system is 90% distributed data infrastructure, memory scheduling, API contracts, latency budgets, and fallback circuits—and only 10% model weights.

The Failure Mode: The Modeling Rabbit Hole Spending your first 15 minutes debating LoRA vs. full fine-tuning without knowing whether the system needs 10 QPS or 10,000 QPS, or whether the p95 latency budget is 50ms or 5 seconds, will fail you the round.

To consistently clear Staff-level loops, you must lead the discussion using a structured 4-Phase Architecture Blueprint.

The 4-Phase System Design Framework

Phase 1: Clarifying & Scoping (Minutes 0–8)

Never start drawing architecture boxes until you have pinned down both Functional and Non-Functional constraints:

  • Traffic & Throughput: Average QPS, peak multiplier, and total daily active users.
  • Latency SLAs:
    • TTFT (Time to First Token): The time from prompt arrival to the first streamed token. For autocomplete, this must be <50ms; for conversational chat, <500ms.
    • TPOT (Time Per Output Token): The inter-token generation speed. Human reading speed is ~25–30 tokens/sec (~33ms/token).
  • Context Window Budgets: Expected prompt input length vs. output generation length.
  • Hardware & Cost Constraints: Self-hosted cluster on proprietary GPUs vs. cloud model APIs.

Phase 2: High-Level Architecture (Minutes 8–22)

Cleanly divide the system into two distinct planes:

  1. The Offline Data Plane: Document extraction, tokenization, semantic chunking, embedding generation, and vector index building. This runs asynchronously via Kafka, Celery, or Spark.
  2. The Online Serving Plane: The real-time path traversed by every user request: API Gateway → Authentication → Guardrails / Prompt Injection Filter → Retrieval Engine → LLM Serving Cluster → Response Streamer.
Staff-Level Seam Principle Always identify the synchronous vs. asynchronous boundary early. Keep the user-facing request loop strictly isolated from heavy compute tasks (such as background indexing or offline eval logging).

Phase 3: Deep Dive into AI Bottlenecks & Scale (Minutes 22–37)

This is where Senior/Staff candidates shine. LLM inference has a unique characteristic:

  • Prefill Phase (Prompt Processing): Compute-bound. Matrix multiplications across all prompt tokens happen simultaneously.
  • Decode Phase (Token Generation): Memory-bandwidth bound. To generate a single new token, all 140GB of model weights (for a 70B FP16 model) and the KV cache must be loaded from GPU HBM into SRAM!

Here you introduce modern systems optimizations:

  • Continuous (Iteration-Level) Batching: Dynamically inserting new requests into the forward pass as soon as existing ones finish, eliminating GPU idle time caused by static batching.
  • PagedAttention (vLLM): Allocating KV cache in non-contiguous virtual memory blocks, eliminating internal fragmentation (which otherwise wastes up to 60–80% of GPU memory).
  • Hybrid Retrieval: Combining sparse BM25 (keyword precision) with dense embeddings (semantic meaning) merged via Reciprocal Rank Fusion (RRF).

Phase 4: Operational Resilience & Evals (Minutes 37–45)

Wrap up by showing production maturity:

  • The Evaluation Flywheel: The "RAG Triad" (Context Relevance, Faithfulness, Answer Relevance) tracked via golden test sets and LLM-as-a-judge.
  • Graceful Degradation: If GPU inference queues back up, fall back to a smaller distilled model (e.g., 8B instead of 70B) or serve semantic cache hits.
